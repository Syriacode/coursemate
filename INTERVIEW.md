# Interview questions: coursemate

## Q1. What happens when you run `coursemate ingest` and then `coursemate ask`?

Answer: `ingest` first calls `store.prepare`, which creates the pgvector extension, an `index_meta` table, the chunks table and an HNSW cosine index, and records which embedding model and dimension built the index (a different model is refused unless I pass `--reset`). It then finds every `.md` and `.txt` file under the path and splits each one by heading, packing paragraphs into chunks of up to about 1000 characters. Each chunk is embedded as the heading, a newline and the text, with the `search_document:` prefix, in batches of 16 with nomic-embed-text through Ollama, and the file's old rows are replaced by the new ones in one transaction, so running ingest twice gives the same index. `ask` embeds the question with the `search_query:` prefix and asks Postgres for the k nearest chunks by cosine distance, turning distance into a score with `1 - distance`. If there are no hits or the best score is below `min_score`, it answers "I don't know" without calling the chat model. Otherwise it builds a prompt with the chunks numbered `[1] source > heading`, calls qwen2.5:3b with temperature 0, an explicit `num_ctx` and a JSON schema, and validates the reply with Pydantic. A reply that is invalid, says not found, has no citations or cites a number that was not retrieved fails closed to "I don't know"; otherwise the CLI prints the answer, the cited sources with their scores, and the token counts.

## Q2. How did you chunk the notes, and how would you choose chunk size and overlap for a different corpus?

Answer: I split each file at markdown headings first and keep the heading path, such as "Lecture 2: Hash Tables > Load factor and resizing", then pack whole paragraphs into chunks of up to 1000 characters; only a paragraph longer than that is cut into windows with 150 characters of overlap. The heading path is embedded with the text and shown in the citation, so a chunk keeps its context and an answer can point to a section. My sample notes produce chunks of 100 to 322 characters, so the windowing and overlap path has only been tested on synthetic text, not on real notes. For a different corpus I would let the document's structure and the embedding model's input limit set the size, then tune it with measurements. For long PDFs I would parse the layout first and chunk by section at roughly 300 to 800 tokens with 10 to 20 percent overlap; for code I would chunk by function or class with the file path and signature as the heading; for slides I would use one slide plus its speaker notes per chunk and merge neighbouring slides, because a single slide is too short to embed well. If chunks are too big, one vector blurs several topics so similarity gets noisy, the prompt costs more, and the model has to find the answer in a lot of text; if they are too small, a rule gets separated from its exception (the late penalty from the grace days) and a chunk can't answer anything on its own. The way to choose is to build a golden set of questions with the chunk that should answer each, and compare recall@k across chunk size and overlap settings.

## Q3. What is an embedding, why cosine similarity, and why Postgres with pgvector instead of a dedicated vector database? What happens if you change the embedding model?

Answer: An embedding is a fixed-length list of numbers (768 here) that a model produces from text, so that texts with similar meaning point in similar directions. I use cosine similarity because it compares direction and ignores length, so a short question can match a long passage; pgvector's `<=>` returns cosine distance and I report `1 - distance` as the score. Scores need care: even for off-topic questions the best chunk scored 0.48 to 0.49, so only the gap between on-topic and off-topic scores means anything. I used Postgres with pgvector because the corpus is small and I wanted vectors next to normal columns, SQL filters (which later become access control by course), transactions for re-ingest, and one system to run and back up, with an HNSW index for fast approximate search. A dedicated vector database makes sense at hundreds of millions of vectors or for specialised features, but it adds another service and a sync problem between the vectors and their metadata. If I change the embedding model, the old vectors become meaningless, because vectors from different models are not comparable and may even have a different number of dimensions. That is why `index_meta` stores the model and dimension, and the CLI refuses to mix them and tells me to re-ingest with `--reset`. After a change I would also re-measure the score ranges, because a new model's scores sit in a different range and `min_score` would need recalibrating.

## Q4. How does CourseMate decide to say "I don't know", what can still go wrong, and how would you measure hallucinations?

Answer: It has two gates. The first runs before the model call: if retrieval returns nothing or the best score is below `min_score`, it answers "I don't know" without paying for a model call. The second runs after: the reply must match a strict JSON schema, say `found: true`, have a non-empty answer, and cite only source numbers that were actually retrieved, and anything else fails closed. The threshold is meant to sit in the gap I measured between on-topic questions, whose top hit scored 0.64 to 0.74, and off-topic ones at 0.48 to 0.49, but that is only 7 questions and a single global value. What can still go wrong: a valid citation does not prove the cited text supports the claim, so an answer can add an unsupported detail; a 3B model sometimes answers from its own knowledge despite the prompt; retrieval can miss the right chunk, which becomes a wrong refusal or a wrong answer; and text inside the notes could try to inject instructions. To measure hallucination I would build a golden set of on-topic and off-topic questions and track the refusal rate on off-topic ones, the answer rate on on-topic ones, recall@k for retrieval on its own, and groundedness, the share of answer claims supported by the cited chunks, judged by people first and later by an LLM judge calibrated against those human labels. Cost matters too: for the same late-project question on the sample notes, `-k 4` used 390 input and about 54 output tokens and `-k 8` used 702 input and 53 output tokens, so doubling k raised the input by 80 percent and gave the same answer from the same cited source, and more chunks can also bury the answer, so I would pick k from recall@k rather than guessing.

## Q5. Design a RAG system for 10,000 course documents across 200 courses and 5,000 student questions a day.

Answer: Scale first: assuming about 50 chunks per document, 10,000 documents is roughly half a million chunks, about 1.5 GB of 768-dimension vectors, and 5,000 questions a day is under 0.1 per second on average with evening and pre-exam peaks of a few per second, so Postgres with pgvector, `tsvector` for keywords and a small worker pool is enough without a dedicated vector database. Ingestion runs through a queue with a parser per type (PDF text with an OCR fallback, one record per slide with its speaker notes, markdown) and structure-aware chunks of about 300 to 800 tokens carrying course, document, page or slide, version and a content hash, and incremental re-indexing re-embeds only documents whose hash changed, replacing each document's chunks in one transaction and deleting those of removed files, as my per-file re-ingest does. Embeddings come from an open model such as bge-m3 or nomic-embed, self-hosted so documents stay on campus, stored with the model name and version so a new model is built as a shadow index and swapped in after evaluation, the same reason my `index_meta` refuses to mix models. Access control is enforced in the query, not the prompt: each request carries the student's enrolled course IDs from the university's identity system, and a `WHERE course_id = ANY(...)` filter (or Postgres row-level security) is applied before ranking, so other courses' chunks never reach the model, and cache keys include the course set. Retrieval is hybrid and scoped to the course the student picked: vector top 50 and keyword top 50 are fused with reciprocal rank fusion and re-ranked by a cross-encoder down to 4 to 6 chunks, with a threshold on the reranker score as the first "I don't know" gate, and the prompt numbers the sources with document title and page, asks for schema-validated JSON with citations, validates them and fails closed, with the UI linking each citation to its page. For local versus hosted models, a self-hosted 7 to 8B model on a GPU keeps data on campus at a fixed cost but follows grounding rules less reliably, while a hosted model is stronger and needs no GPU operations but sends the question and retrieved passages to a vendor, so I would use hosted under a contract with no training on our data and zero retention unless policy requires local; I would budget a p95 latency of about 5 seconds, with retrieval and reranking around half a second and the rest streamed generation, compute cost per question from measured tokens times price times 5,000 a day, and cache query embeddings and answers (keyed by normalised question, course and index version) plus the provider's prompt cache for the fixed system prompt. Before each release a CI gate like question-triage's runs a golden set per course type and blocks on thresholds for retrieval recall@k, groundedness (an LLM judge calibrated against human labels) and the refusal rate on off-topic questions, and any change to the chunker, embedding model, reranker or prompt must pass it. For privacy, only course materials are indexed, never student records, grades or submissions, questions are logged with a pseudonymous ID and a retention limit, and only the question plus retrieved instructor material may go to a vendor, under a data-processing agreement and with nothing that identifies a student; for monitoring I would track per-stage latency, retrieval scores, refusal rate, citation-validation failures, token cost, thumbs up or down, clusters of unanswered questions that show gaps in the materials, and index freshness, alerting on drift.

## Retrieval (Week 2 Thu)

### Q6. What's the difference between keyword (BM25) and vector search? Give one question from your golden set where each one wins, and why.

Answer: BM25 keyword search scores a chunk by the words it shares with the question: a word counts more if it is rare across the notes, repeating it helps but with diminishing returns, and long chunks are discounted, and my version has no stemming, so "labs" does not match "lab". Vector search turns the question and every chunk into embeddings and compares their direction, so it can match meaning even when no words are shared. Vector search wins q25, "The automatic checks on my repo keep failing, what should I do?": the right section, Submitting work, says "autograder" and "fails", so it shares no word with the question, and keyword search missed it completely while vector search ranked it first. Keyword search is meant to win on exact terms like q08, "When is Lab 4 due?", where "lab", "4" and "due" are rare and exact, but in my results vector search also ranked that section first, so they tie. In fact keyword search never found a section that vector search missed; its only strict win was q19, by one rank, and that came from filler words like "or", "that" and "other" that are not in my small stopword list, so I don't count it as real. Overall, with nomic-embed-text, vector search had recall@3 of 0.96 against 0.76 for keyword, and 0.92 against 0.50 on paraphrase questions, while both scored 1.00 on questions that reuse the notes' own words. So keyword search is cheap and good for exact names, numbers and codes, while vector search is what handles a student's own phrasing.

### Q7. How does hybrid search with Reciprocal Rank Fusion work, and why combine by rank instead of adding scores?

Answer: Reciprocal Rank Fusion combines several ranked lists using only the ranks: each list gives a chunk 1 / (60 + its rank in that list), and a chunk's score is the sum over the lists. A chunk counts as the same chunk if its source, heading and text match, and in my code each method first returns 20 candidates, so a chunk that is sixth in one list and second in the other can still be fused. For example, with vector results [A, B] and keyword results [B, C], B gets 1/62 + 1/61, A gets 1/61 and C gets 1/62, so B comes first because both methods like it. I combine by rank because the scores live on different scales: my cosine scores sat around 0.5 to 0.7, while BM25 scores went up to about 5.8, so adding them would let keyword search dominate for no good reason. The constant 60 flattens the curve so that first place does not count far more than second, which is why fused scores are small, about 0.03. In my measurements hybrid did worse than vector, with recall@3 of 0.84 against 0.96, because RRF gives the weak keyword list as much say as the vector list. It pushed q09, q15 and q18 out of the top 3 and only improved q19, from second to first, so hybrid is something to measure on your own data and not an automatic upgrade.

### Q8. How did you measure retrieval? Explain recall@k and MRR, and why you measure retrieval separately from the final answers.

Answer: I wrote a golden set of 25 questions, 13 that reuse the notes' words and 12 paraphrases, and each one is labelled with the file and section that answers it, not a chunk id, so changing the chunking does not break the labels. The set has to be marked reviewed before the loader accepts it, so I checked every question by hand first. For each question I run the search and record the rank of the first right section in the top 5. Recall@k is the share of questions whose right section is in the top k, and MRR, mean reciprocal rank, is the average of 1 divided by that rank, counting 0 for a miss, so it rewards putting the right section first. For vector search my numbers were recall@1 0.84, recall@3 0.96, recall@5 1.00 and MRR 0.90. I measure retrieval separately from the final answers because it is cheap, repeatable and needs no chat model, and when an answer is wrong it tells me whether search failed to find the right text or the model misused it. The caveat is size: 25 questions over 8 short notes means one question moves recall by 4 points, so I treat small differences as hints, not proof.

### Q9. What is a reranker, when would you add one, and how would you prove it helps?

Answer: A reranker is a second model, usually a cross-encoder, that reads the question and one chunk together and gives the pair a relevance score. It is more accurate than comparing two separate vectors because it can look at both texts at once, but it is too slow to run on every chunk, so it only reorders a short candidate list, for example the top 20 to 50 from hybrid search. I would add one when the right chunk is usually among the candidates but not at the top, and my results hint at that: vector recall@5 is 1.00 but recall@1 is 0.84, because the right section was ranked 4th for q13, 3rd for q15 and q18, and 2nd for q19. To prove it helps, I would run the same golden set with the same candidates, once without and once with the reranker, and compare recall@1, recall@3 and MRR. Then I would read the individual questions it fixed and the ones it broke, because an average can hide a new failure. I would also measure the extra latency and cost per question, since a small gain is not worth a big slowdown. With only 25 questions, a gain of one or two is within noise, so I would grow the golden set first, and I have not added a reranker yet; it is in my known limitations.

### Q10. LLM system design: users of a RAG system over 10,000 documents complain that answers are "often wrong". How do you find out whether retrieval or generation is the problem, and what would you change in each case?

Answer: I would not guess; I would first define "wrong" from real data by collecting a sample of failing questions, for example thumbs-down votes and support tickets, and labelling each one by hand. For each question I would ask three things in order: does the corpus contain the answer at all, was the right chunk among the retrieved top k, and if it was, did the model still answer wrongly or without support. If the answer is not in the corpus, the fix is content, not code; if the chunk was not retrieved, retrieval is the problem; if it was retrieved but the answer is wrong, generation is the problem. I would turn those labelled questions into a golden set and track recall@k for retrieval and groundedness, the share of answer claims supported by the cited text, for generation. For retrieval problems I would try hybrid search, better chunking with headings kept, query rewriting, more candidates with a reranker, metadata filters such as the course, a better embedding model, and filling content gaps, measuring each change on the golden set. For generation problems I would tighten the prompt and the output schema, validate that citations point at retrieved sources and support the claim, send fewer and cleaner chunks so distractors do not mislead the model, lower the temperature, make the system refuse when the sources do not support an answer, and try a stronger model. I would also slice the failures by course and by question type, because "often wrong" is usually a few specific categories and not everything. Finally, I would add every fixed failure to the golden set so it can't quietly break again.
