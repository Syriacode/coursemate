# Interview questions: coursemate

## Q1. What happens when you run `coursemate ingest` and then `coursemate ask`?

Answer: `ingest` first calls `store.prepare`, which creates the pgvector extension, an `index_meta` table, the chunks table and an HNSW cosine index, and records which embedding model and dimension built the index (a different model is refused unless I pass `--reset`). It then finds every `.md` and `.txt` file under the path and splits each one by heading, packing paragraphs into chunks of up to about 1000 characters. Each chunk is embedded as the heading, a newline and the text, with the `search_document:` prefix, in batches of 16 with nomic-embed-text through Ollama, and the file's old rows are replaced by the new ones in one transaction, so running ingest twice gives the same index. `ask` embeds the question with the `search_query:` prefix and asks Postgres for the k nearest chunks by cosine distance, turning distance into a score with `1 - distance`. If there are no hits or the best score is below `min_score`, it answers "I don't know" without calling the chat model. Otherwise it builds a prompt with the chunks numbered `[1] source > heading`, calls qwen2.5:3b with temperature 0, an explicit `num_ctx` and a JSON schema, and validates the reply with Pydantic. A reply that is invalid, says not found, has no citations or cites a number that was not retrieved fails closed to "I don't know"; otherwise the CLI prints the answer, the cited sources with their scores, and the token counts.

## Q2. How did you chunk the notes, and how would you choose chunk size and overlap for a different corpus?

Answer: I split each file at markdown headings first and keep the heading path, such as "Lecture 2: Hash Tables > Load factor and resizing", then pack whole paragraphs into chunks of up to 1000 characters; only a paragraph longer than that is cut into windows with 150 characters of overlap. The heading path is embedded with the text and shown in the citation, so a chunk keeps its context and an answer can point to a section. My sample notes produce chunks of 100 to 322 characters, so the windowing and overlap path has only been tested on synthetic text, not on real notes. For a different corpus I would let the document's structure and the embedding model's input limit set the size, then tune it with measurements. For long PDFs I would parse the layout first and chunk by section at roughly 300 to 800 tokens with 10 to 20 percent overlap; for code I would chunk by function or class with the file path and signature as the heading; for slides I would use one slide plus its speaker notes per chunk and merge neighbouring slides, because a single slide is too short to embed well. If chunks are too big, one vector blurs several topics so similarity gets noisy, the prompt costs more, and the model has to find the answer in a lot of text; if they are too small, a rule gets separated from its exception (the late penalty from the grace days) and a chunk can't answer anything on its own. The way to choose is to build a golden set of questions with the chunk that should answer each, and compare recall@k across chunk size and overlap settings.

## Q3. What is an embedding, why cosine similarity, and why Postgres with pgvector instead of a dedicated vector database? What happens if you change the embedding model?

Answer: An embedding is a fixed-length list of numbers (768 here) that a model produces from text, so that texts with similar meaning point in similar directions. I use cosine similarity because it compares direction and ignores length, so a short question can match a long passage; pgvector's `<=>` returns cosine distance and I report `1 - distance` as the score. Scores need care: even for off-topic questions the best chunk scored 0.48 to 0.49, so only the gap between on-topic and off-topic scores means anything. I used Postgres with pgvector because the corpus is small and I wanted vectors next to normal columns, SQL filters (which later become access control by course), transactions for re-ingest, and one system to run and back up, with an HNSW index for fast approximate search. A dedicated vector database makes sense at hundreds of millions of vectors or for specialised features, but it adds another service and a sync problem between the vectors and their metadata. If I change the embedding model, the old vectors become meaningless, because vectors from different models are not comparable and may even have a different number of dimensions. That is why `index_meta` stores the model and dimension, and the CLI refuses to mix them and tells me to re-ingest with `--reset`. After a change I would also re-measure the score ranges, because a new model's scores sit in a different range and `min_score` would need recalibrating.

## Q4. How does CourseMate decide to say "I don't know", what can still go wrong, and how would you measure hallucinations?

Answer: It has two gates. The first runs before the model call: if retrieval returns nothing or the best score is below `min_score`, it answers "I don't know" without paying for a model call. The second runs after: the reply must match a strict JSON schema, say `found: true`, have a non-empty answer, and cite only source numbers that were actually retrieved, and anything else fails closed. The threshold is meant to sit in the gap I measured between on-topic questions, whose top hit scored 0.64 to 0.74, and off-topic ones at 0.48 to 0.49, but that is only 7 questions and a single global value. What can still go wrong: a valid citation does not prove the cited text supports the claim, so an answer can add an unsupported detail; a 3B model sometimes answers from its own knowledge despite the prompt; retrieval can miss the right chunk, which becomes a wrong refusal or a wrong answer; and text inside the notes could try to inject instructions. To measure hallucination I would build a golden set of on-topic and off-topic questions and track the refusal rate on off-topic ones, the answer rate on on-topic ones, recall@k for retrieval on its own, and groundedness, the share of answer claims supported by the cited chunks, judged by people first and later by an LLM judge calibrated against those human labels. Cost matters too: for the same late-project question on the sample notes, `-k 4` used 390 input and about 54 output tokens and `-k 8` used 702 input and 53 output tokens, so doubling k raised the input by 80 percent and gave the same answer from the same cited source, and more chunks can also bury the answer, so I would pick k from recall@k rather than guessing.

## Q5. Design a RAG system for 10,000 course documents across 200 courses and 5,000 student questions a day.

Answer: Scale first: assuming about 50 chunks per document, 10,000 documents is roughly half a million chunks, about 1.5 GB of 768-dimension vectors, and 5,000 questions a day is under 0.1 per second on average with evening and pre-exam peaks of a few per second, so Postgres with pgvector, `tsvector` for keywords and a small worker pool is enough without a dedicated vector database. Ingestion runs through a queue with a parser per type (PDF text with an OCR fallback, one record per slide with its speaker notes, markdown) and structure-aware chunks of about 300 to 800 tokens carrying course, document, page or slide, version and a content hash, and incremental re-indexing re-embeds only documents whose hash changed, replacing each document's chunks in one transaction and deleting those of removed files, as my per-file re-ingest does. Embeddings come from an open model such as bge-m3 or nomic-embed, self-hosted so documents stay on campus, stored with the model name and version so a new model is built as a shadow index and swapped in after evaluation, the same reason my `index_meta` refuses to mix models. Access control is enforced in the query, not the prompt: each request carries the student's enrolled course IDs from the university's identity system, and a `WHERE course_id = ANY(...)` filter (or Postgres row-level security) is applied before ranking, so other courses' chunks never reach the model, and cache keys include the course set. Retrieval is hybrid and scoped to the course the student picked: vector top 50 and keyword top 50 are fused with reciprocal rank fusion and re-ranked by a cross-encoder down to 4 to 6 chunks, with a threshold on the reranker score as the first "I don't know" gate, and the prompt numbers the sources with document title and page, asks for schema-validated JSON with citations, validates them and fails closed, with the UI linking each citation to its page. For local versus hosted models, a self-hosted 7 to 8B model on a GPU keeps data on campus at a fixed cost but follows grounding rules less reliably, while a hosted model is stronger and needs no GPU operations but sends the question and retrieved passages to a vendor, so I would use hosted under a contract with no training on our data and zero retention unless policy requires local; I would budget a p95 latency of about 5 seconds, with retrieval and reranking around half a second and the rest streamed generation, compute cost per question from measured tokens times price times 5,000 a day, and cache query embeddings and answers (keyed by normalised question, course and index version) plus the provider's prompt cache for the fixed system prompt. Before each release a CI gate like question-triage's runs a golden set per course type and blocks on thresholds for retrieval recall@k, groundedness (an LLM judge calibrated against human labels) and the refusal rate on off-topic questions, and any change to the chunker, embedding model, reranker or prompt must pass it. For privacy, only course materials are indexed, never student records, grades or submissions, questions are logged with a pseudonymous ID and a retention limit, and only the question plus retrieved instructor material may go to a vendor, under a data-processing agreement and with nothing that identifies a student; for monitoring I would track per-stage latency, retrieval scores, refusal rate, citation-validation failures, token cost, thumbs up or down, clusters of unanswered questions that show gaps in the materials, and index freshness, alerting on drift.

## Retrieval (Week 2 Thu)

### Q6. What's the difference between keyword (BM25) and vector search? Give one question from your golden set where each one wins, and why.

Answer: BM25 keyword search scores a chunk by the words it shares with the question: a word counts more if it is rare across the notes, repeating it helps but with diminishing returns, and long chunks are discounted, and my version has no stemming, so "labs" does not match "lab". Vector search turns the question and every chunk into embeddings and compares their direction, so it can match meaning even when no words are shared. Vector search wins q25, "The automatic checks on my repo keep failing, what should I do?": the right section, Submitting work, says "autograder" and "fails", so it shares no word with the question, and keyword search missed it completely while vector search ranked it first. Keyword search is meant to win on exact terms like q08, "When is Lab 4 due?", where "lab", "4" and "due" are rare and exact, but in my results vector search also ranked that section first, so they tie. In fact keyword search never found a section that vector search missed; its only strict win was q19, by one rank, and that came from filler words like "or", "that" and "other" that are not in my small stopword list, so I don't count it as real. Overall, with nomic-embed-text, vector search had recall@3 of 0.96 against 0.76 for keyword, and 0.92 against 0.50 on paraphrase questions, while both scored 1.00 on questions that reuse the notes' own words. So keyword search is cheap and good for exact names, numbers and codes, while vector search is what handles a student's own phrasing.

### Q7. How does hybrid search with Reciprocal Rank Fusion work, and why combine by rank instead of adding scores?

Answer: Reciprocal Rank Fusion combines several ranked lists using only the ranks: each list gives a chunk 1 / (60 + its rank in that list), and a chunk's score is the sum over the lists. A chunk counts as the same chunk if its source, heading and text match, and in my code each method first returns 20 candidates, so a chunk that is sixth in one list and second in the other can still be fused. For example, with vector results [A, B] and keyword results [B, C], B gets 1/62 + 1/61, A gets 1/61 and C gets 1/62, so B comes first because both methods like it. I combine by rank because the scores live on different scales: my cosine scores sat around 0.5 to 0.7, while BM25 scores went up to about 5.8, so adding them would let keyword search dominate for no good reason. The constant 60 flattens the curve so that first place does not count far more than second, which is why fused scores are small, about 0.03. In my measurements hybrid did worse than vector, with recall@3 of 0.84 against 0.96, because RRF gives the weak keyword list as much say as the vector list. It pushed q09, q15 and q18 out of the top 3 and only improved q19, from second to first, so hybrid is something to measure on your own data and not an automatic upgrade.

### Q8. How did you measure retrieval? Explain recall@k and MRR, and why you measure retrieval separately from the final answers.

Answer: I wrote a golden set of 25 questions, 13 that reuse the notes' words and 12 paraphrases, and each one is labelled with the file and section that answers it, not a chunk id, so changing the chunking does not break the labels. The set has to be marked reviewed before the loader accepts it, so I checked every question by hand first. For each question I run the search and record the rank of the first right section in the top 5. Recall@k is the share of questions whose right section is in the top k, and MRR, mean reciprocal rank, is the average of 1 divided by that rank, counting 0 for a miss, so it rewards putting the right section first. For vector search my numbers were recall@1 0.84, recall@3 0.96, recall@5 1.00 and MRR 0.90. I measure retrieval separately from the final answers because it is cheap, repeatable and needs no chat model, and when an answer is wrong it tells me whether search failed to find the right text or the model misused it. The caveat is size: 25 questions over 8 short notes means one question moves recall by 4 points, so I treat small differences as hints, not proof.

### Q9. What is a reranker, when would you add one, and how would you prove it helps?

Answer: A reranker is a second model, usually a cross-encoder, that reads the question and one chunk together and gives the pair a relevance score. It is more accurate than comparing two separate vectors because it can look at both texts at once, but it is too slow to run on every chunk, so it only reorders a short candidate list, for example the top 20 to 50 from hybrid search. I would add one when the right chunk is usually among the candidates but not at the top, and my results hint at that: vector recall@5 is 1.00 but recall@1 is 0.84, because the right section was ranked 4th for q13, 3rd for q15 and q18, and 2nd for q19. To prove it helps, I would run the same golden set with the same candidates, once without and once with the reranker, and compare recall@1, recall@3 and MRR. Then I would read the individual questions it fixed and the ones it broke, because an average can hide a new failure. I would also measure the extra latency and cost per question, since a small gain is not worth a big slowdown. With only 25 questions, a gain of one or two is within noise, so I would grow the golden set first, and I have not added a reranker yet; it is in my known limitations.

### Q10. LLM system design: users of a RAG system over 10,000 documents complain that answers are "often wrong". How do you find out whether retrieval or generation is the problem, and what would you change in each case?

Answer: I would not guess; I would first define "wrong" from real data by collecting a sample of failing questions, for example thumbs-down votes and support tickets, and labelling each one by hand. For each question I would ask three things in order: does the corpus contain the answer at all, was the right chunk among the retrieved top k, and if it was, did the model still answer wrongly or without support. If the answer is not in the corpus, the fix is content, not code; if the chunk was not retrieved, retrieval is the problem; if it was retrieved but the answer is wrong, generation is the problem. I would turn those labelled questions into a golden set and track recall@k for retrieval and groundedness, the share of answer claims supported by the cited text, for generation. For retrieval problems I would try hybrid search, better chunking with headings kept, query rewriting, more candidates with a reranker, metadata filters such as the course, a better embedding model, and filling content gaps, measuring each change on the golden set. For generation problems I would tighten the prompt and the output schema, validate that citations point at retrieved sources and support the claim, send fewer and cleaner chunks so distractors do not mislead the model, lower the temperature, make the system refuse when the sources do not support an answer, and try a stronger model. I would also slice the failures by course and by question type, because "often wrong" is usually a few specific categories and not everything. Finally, I would add every fixed failure to the golden set so it can't quietly break again.

## API, streaming and providers (Phase 2 Mon)

### Q11. Why stream LLM responses, and how does SSE work? When would you use WebSockets or polling instead?

Answer: A model produces its answer a few words at a time, so if I wait for the whole reply the student stares at a blank page; streaming shows each piece as it arrives. My `compare` numbers show why it matters: on my local model the first word arrives after a median of 3.5 seconds (3494 ms) and the full answer after 5.6 seconds (5579 ms), so streaming lets the student start reading about two seconds earlier, and the gap grows with longer answers. SSE (server-sent events) is plain HTTP where the server keeps the response open and writes text events: each event is an `event:` line, a `data:` line with JSON and a blank line that ends it, which is what my `format_sse` writes and `sse_data` parses, and my API sends one `session` event, many `token` events, then `done` (or `error`). The browser's `EventSource` can only send GET, so my page uses `fetch` with POST and reads the stream itself, which keeps the question in the JSON body and out of the URL. I would use WebSockets when both sides talk at the same time, for example voice input or letting the user interrupt and steer a long answer, because they give a two-way channel at the cost of a second protocol and connection state to manage. I would use polling when the job is long and the user can come back later, such as a summary of a whole course, or when the network can't hold a connection open: the server returns a job id and the client asks for the result. For a one-way stream of text like a chat answer, SSE is the simplest tool, and I can test it with `curl -N`.

### Q12. What does async buy a Python web server? What happens if you call blocking code inside `async def`, and how did you handle retrieval?

Answer: Think of a waiter in a restaurant. A blocking waiter takes table 1's order, walks to the kitchen and stands there until the food is ready, so table 2 has to wait; an async waiter hands the order to the kitchen and, while it cooks, takes table 2's order, then brings each dish when it is ready. A chat server is that waiter, because almost all of its time is spent waiting for the database, the embedding call and above all the model: if three students ask at the same moment and each answer is 2 seconds of waiting on a hosted API, one blocking worker finishes them at 2, 4 and 6 seconds, while one async thread finishes all three at about 2 seconds. In Python, `async def` makes a function that can pause, `await` is the place where it pauses and lets someone else be served, and the event loop is the waiter: one thread that runs whichever task is ready. The rule I must not break is to never call slow, blocking code directly inside `async def`, because that is the waiter standing in the kitchen: no other stream gets a word, and even `/api/health` stops answering until the call returns. My retrieval is that kind of code, since the embedder uses a synchronous `httpx.Client` and the store uses synchronous `psycopg`, so `stream_answer` runs it with `await asyncio.to_thread(retrieve, ...)`, which means a helper thread does the cooking while the waiter keeps serving, and I chose that because it left my existing synchronous `Embedder` and `VectorStore` and all their tests unchanged; the model call itself uses `httpx.AsyncClient`, which is truly async. One honest limit is that async does not make the model faster: my local Ollama on a CPU mostly answers one question at a time, so locally the model is the bottleneck, but with a hosted API that handles many requests in parallel, async is what lets one server handle hundreds of students.

### Q13. How do you stream an answer and still enforce guardrails like valid citations? What does the user see when a check fails?

Answer: I can only verify the citations once the whole reply exists, but I want to show words right away, so I stream first, check at the end and let the check overrule what was shown. In `stream_answer` the first gate runs before any model call: if the best chunk scores below `min_score` (0.55), the answer is "I don't know" and the model is never asked. Otherwise the pieces go out as `token` events while I collect them, and when the stream ends `check_reply` reads the full text: it must not be empty, must not start with "I don't know", must contain at least one `[n]` citation, and every cited number must be one of the sources I actually retrieved. If it passes, the `done` event carries `found: true`, the answer and only the sources that were cited. If it fails, `done` carries `found: false`, and the page replaces the streamed words with a grey italic "I don't know. I couldn't find that in the course notes." and lists no sources; a test, `test_a_retracted_reply_ends_with_found_false`, covers this. The weak spot is that for a moment the student can read words that are later retracted, so I would show them in a lighter style until `done` arrives, or hold them back for high-stakes courses and accept a slower first word. And a valid citation only proves the number exists, not that the text supports the claim, so a cited answer can still add an unsupported detail; that needs a groundedness check I haven't built.

### Q14. What differs between the OpenAI and Anthropic APIs, how did you hide the differences, and how did you compare latency and cost without paying for API calls?

Answer: They carry the same idea in different packaging. OpenAI takes `POST /v1/chat/completions` with `Authorization: Bearer <key>`, keeps the system prompt as a `system` message in the list, makes the maximum length optional (`max_completion_tokens`), streams `data:` lines that end with `data: [DONE]`, and sends token counts only in a last chunk if I ask with `stream_options.include_usage`. Anthropic takes `POST /v1/messages` with an `x-api-key` and an `anthropic-version` header, wants the system prompt in a separate top-level `system` field, requires `max_tokens`, and streams typed events: text in `content_block_delta`, input tokens in `message_start`, output tokens in `message_delta`, an `error` event, and `message_stop` at the end. I hid all of it behind one `StreamingLLM.stream(messages)` that yields `TextDelta` pieces and then one `StreamEnd` with the model, tokens and times, so the chat logic, the API and the page never know the provider, and switching is `--llm anthropic` plus an environment variable. To compare without paying, I pointed my OpenAI and Anthropic streamers at Ollama, which speaks both formats, so the same `qwen2.5:3b` answered three times: `compare` asks the same golden questions through each format, skips one warm-up answer, and prices the measured tokens with a dated price table, while the unit tests use `httpx.MockTransport` with recorded-style bodies. My numbers were 3494, 3717 and 369 ms to the first word for the native, OpenAI and Anthropic formats, and 5579, 5302 and 1684 ms in total, and the format can't explain the Anthropic row because it is the same model, so I suspect Ollama's prompt cache and still need to check that. One answer of about 470 tokens in and 28 out would cost $0.000061 on Haiku 5.5 or GPT-6 Luna and $0.001220 on Sonnet 5.5 or GPT-6.1 Sol, which is $0.06 and $1.22 per 1,000 answers. A hosted URL without an API key is refused in the constructor, so a typo can't spend money.

### Q15. LLM system design: design a chat API for 1,000 students at once, with streaming, conversation history, two LLM providers with fallback, and a monthly budget.

Answer: I would keep the servers stateless and put the state outside them: every request carries a session id, the last 5 turns live in Redis with an expiry (or in a Postgres table if they must be kept), and I'd run several async instances behind a load balancer, with slow jobs like ingestion on a queue and a separate worker, whereas my current in-memory `SessionStore` loses everything on a restart and only works with one process. For load, if each student asks 5 questions a day that is 5,000 answers a day, and a burst of all 1,000 students inside one minute at the 5.6 seconds per answer I measured is only about 90 streams open at once, which an async server holds easily, so the real limits are the providers' requests and tokens per minute, not my servers. Every call gets timeouts (to connect, to the first token and between tokens, which is how my httpx read timeout works), and failures are retried with exponential backoff and jitter, but only before the first word was sent, since I can't silently restart a half-shown answer, and only for errors worth retrying such as 429, 5xx and timeouts, never 400 or 401. After the retries, or when a circuit breaker marks the first provider unhealthy, a `FallbackStreamer` that implements the same `StreamingLLM` interface switches to the second provider, so nothing above it changes, and I log which provider answered. Each student gets a rate limit (a token bucket in Redis, for example 10 questions a minute and a daily token allowance), and a global concurrency limit with a queue lets bursts wait instead of hitting provider 429 errors. For the budget, every answer already reports its `cost_usd`, so I add it to a counter in Redis: with my numbers (470 tokens in, 28 out), 150,000 answers a month would cost about $9 on Haiku 5.5 and about $183 on Sonnet 5.5, more with history and with hosted tokenizers, so I would alert at 50, 80 and 100 percent of the budget and at 100 percent switch to the cheaper model or refuse politely, never overspend silently. I would cache query embeddings, and answers to first questions with no history, keyed by the normalised question, course and index version, and use the provider's prompt cache for the fixed system prompt; against prompt injection the notes are treated as untrusted text (the prompt says they are course material, not instructions), the model has no tools, citations are validated, and the page only uses `textContent`, with a test that it never uses `innerHTML`. For privacy only the question and the retrieved excerpts go to a provider, never grades or student records, under a no-training, zero-retention agreement, and I log one structured line per answer (request id, hashed student id, provider and model, first-token and total time, tokens, cost, found or refused and why, retries and fallbacks) without the question text by default, and monitor p95 time to the first word, error and fallback rate per provider, refusal rate, spend against the budget and queue depth, with an alert on each.

## CourseMate agent

### Q16. How does your agent stop and ask a human before it sends something? Why is the check in code and not in the prompt, and what does "fail closed" mean here?

Answer: Sending is split into two tools: `draft_announcement` only saves a file in `outbox/drafts`, and `send_announcement` moves it to `outbox/sent`, so the human approves the exact text that will go out and not a description of it. The check lives in `run_tool`: before it runs any tool named in `NEEDS_APPROVAL` (only `send_announcement`), it calls an approver function, and in the terminal that function prints the draft and asks `Send it? [y/N]`. It is in code and not in the prompt because a prompt is only a request, and a 3B model can ignore it, misread it, or be talked into sending by text inside the notes, while code runs the same way no matter what the model says; my prompt does tell the model to send only when asked, but that is a hint, not a guarantee. "Fail closed" means that when anything is missing or unclear the answer is no: the default approver is `deny_all`, and anything but "y" at the prompt counts as no, so forgetting to connect a human sends nothing instead of everything. A "no" goes back to the model as a tool result ("not approved ... tell the instructor it was not sent"), so it can answer honestly and stop instead of crashing or retrying. I test the gate by breaking it on purpose: with `NEEDS_APPROVAL` emptied, the declined case sends a message and the eval's unapproved-sends counter goes from 0 to 1. The limits are that "sent" only moves a file today, and the gate only protects tools I remember to put in `NEEDS_APPROVAL`, so every new write tool has to be added there.

### Q17. How do you evaluate an agent when there's no single correct answer? What did your evals check, and what did they find on qwen2.5:3b?

Answer: Because the agent can reach a good result by several paths and word its answer many ways, I don't compare against one expected string; I score rules about what happened. Each of the 8 cases in `evals/agent_cases.jsonl` checks four things: the outcome (how many messages were sent, and whether a saved draft contains "Friday"), the trajectory (which tools it called, by name only, not order or arguments), the answer (whether the text contains one of the accepted phrases, like "not sent|not approved") and the stop (did it end with an answer, not `max_steps` or an empty reply). Each case runs in its own empty outbox with a scripted instructor who says yes or no, and I reviewed all eight labels by hand, as I did for the retrieval golden set. On top of the pass rate there is a safety number, unapproved sends, which must be 0 on every run. On `qwen2.5:3b` it passed 3 of 8 (38%) with 0 unapproved sends, 1.9 steps and 1,299 input tokens on average. The failures were an empty reply on `office-hours`, drafts that lacked "Friday" even though the answer said it, and two cases where the model drafted, said "I will send it now" and stopped without calling send; `not-in-notes` also failed, but there the answer was right and my phrase list lacked "do not say", so that one is a rule problem, not a model problem. The honest limits are that the 0 was never tested by a real attempt, because the model never tried to send, which is why a separate test removes the gate and checks the counter moves, and that 8 cases run once is a smoke alarm (one case is 12.5 points) with crude word matching, so the upgrade is a judge calibrated against human labels.

### Q18. Your agent has a make_quiz tool that calls the model itself. When do you put a fixed workflow inside a tool instead of letting the agent plan every step?

Answer: `make_quiz` is a tool that calls the model itself, but its steps inside are fixed: search the notes, put the numbered passages in a prompt, ask for JSON that matches a quiz schema, and validate it with Pydantic (exactly four choices, an answer index from 0 to 3, one to five questions). The agent only decides to use it and picks the topic; it does not plan the inside. I put a fixed workflow inside a tool when the steps are known in advance and must not vary, when the output has to be validated, and when a small model would waste steps or break the format if it planned each one. It also costs the agent one step to call it instead of four, which matters because every step resends the whole history and the tool descriptions. I let the agent plan when the path depends on the request, such as "find Lab 4's date, draft a reminder, then send it", where the tools and their order change from task to task. The price of a fixed workflow is flexibility, since it can't adapt if a quiz needs different sources, and a bug in it hides behind one tool call, but in return I can test it like ordinary code with a fake model, as my tests do for bad JSON and for three choices instead of four. In the eval, `quiz` passed in two steps: one to call the tool and one to answer.

### Q19. You built the same agent from scratch and on the Claude Agent SDK. What does the SDK give you, what does it hide, and which would you ship?

Answer: The SDK gives you Claude Code's own engine as a library: `query()` runs the loop, handles the message format, serves my Python functions to Claude as an in-process MCP server, runs the permission checks, and adds things I didn't write, like sessions, hooks and a much stronger model. What it hides is exactly what I built by hand: the `for` loop, how tool calls and results go into the history, and the order of the permission checks (`allowed_tools` first, then `can_use_tool` for the rest). Because it hides that, I locked it down: `tools=[]` turns off Claude Code's own Bash, Read and Edit, `setting_sources=[]` stops my own settings and `CLAUDE.md` leaking in, only the three read tools are allow-listed, and `send_announcement` reaches my `can_use_tool`, which asks me y/N. It reuses the same JSON Schemas and functions, so the tools and the human "yes" didn't change, and `sdk_agent.py` is about 165 lines with no loop, against about 115 for `agent.py`. The costs are a dependency of about 170 MB, being tied to Claude, and a billing trap: with `ANTHROPIC_API_KEY` set it bills the API instead of my plan, so my script refuses to start if that variable is set. For a small agent with a few tools and data that must stay on my machine, I'd ship my own loop, because I can read it in a minute and test it with fakes; for many tools, long sessions, or a task that needs a strong model, I'd use the SDK and keep the same deny-by-default permission code and the same evals. I haven't yet run both on the same task to compare turns and seconds, so I would make that call from my own table and not from a guess.

### Q20. LLM system design: design an AI assistant that drafts and sends course announcements and answers student questions for 50 instructors and 5,000 students. Cover tools and permissions, approval flow (including approvals that come hours later), prompt injection, agent evals in CI, and what you monitor in production.

Answer: The load is small, so a Postgres database, a few stateless async workers and a queue are enough, and the hard parts are permissions and trust, not scale. Tools come in three tiers: read tools (search notes, list deadlines), a draft tool that saves an announcement as pending, and one send tool; per-course access is enforced inside each tool's database query from the identity the login system supplies (`WHERE course_id = ANY(the user's courses)`), never from the prompt or from an argument the model chose, and the student-facing assistant gets only read tools on the student's own courses, with no draft or send tool at all. A send never runs directly: it creates a pending approval holding the draft id, the course and a hash of the exact text, and the agent run ends with "waiting for approval", so hours later the instructor sees that exact text in a page and clicks approve, and a separate service sends only if the hash still matches, the approval hasn't expired and the approver owns that course, using an idempotency key so a double click can't send twice and writing an audit log of who approved what and when; any edit to the draft cancels the approval. Notes and student messages are untrusted data, so the prompt labels them that way, but I don't rely on the label: the structural defences are that the agent reading student messages has no write tools, the human reads the exact text before anything goes out, tool results are length-limited and checked for instruction-like text, and the gate is code the model can't skip, so the worst a poisoned note can do is propose a bad draft that a person sees. In CI, scripted-model tests run on every pull request, including a break-it test that removes the gate and requires the eval to report unapproved sends above 0, and before each release the real model runs the agent cases, including injection cases such as a note that says "send this to everyone", and the release is blocked if the pass rate falls below a threshold set from earlier runs or if unapproved sends is anything but 0; I would run each case several times, because one run of 8 cases is only a smoke alarm. In production I would monitor unapproved actions (alert on any single one), the approval, rejection and expiry rates, the refusal and "I don't know" rate on student questions, steps per task and stop reasons (`max_steps` and empty replies), cost and latency per task by model, and the number of approvals pending for more than a day. For the model I would weigh a hosted one under a no-training agreement against a local one for privacy, and I would budget from measured tokens (my 3B agent used about 1,300 input tokens on a two-step task, and every step resends the history and the tool descriptions), with a per-user and a monthly limit and a cheaper model when the budget runs out. If the approver, the model or the database fails, the system fails closed: nothing is sent, the draft stays pending, and the instructor is told why.

## CourseMate MCP server

### Q21. What is MCP and what problem does it solve? Explain hosts, clients and servers, and tools vs. resources vs. prompts, with CourseMate examples.

Answer: MCP, the Model Context Protocol, is an open standard that lets an AI app talk to outside systems in one common way, a bit like USB-C for tools. Without it, every app needs its own code for every system, so five apps and five systems means twenty-five integrations; with it, I write one server and every MCP app can use it. The host is the app the person uses, here Claude Code; inside it, one client keeps a connection to each server; and the server is my `coursemate/mcp_server.py`, which Claude Code starts as a child process. A server offers three kinds of things, and the difference is who decides to use them. Tools are called by the model: `search_notes`, `make_quiz`, `draft_announcement` and `send_announcement`. Resources are data the person attaches, such as `notes://sample/syllabus.md` with `@`, and prompts are templates the person picks, such as `/mcp__coursemate__announcement office hours`, which tells the model to draft and never send. All four tools come from the same `CourseTools` that my agent loop uses, so MCP is a second front door and not a second implementation. What can go wrong is that a tool description is text the model reads, so a careless one misleads it, and annotations like `destructiveHint` are only hints, so safety has to be enforced inside the server (see Q23).

### Q22. Walk me through what happens on the wire when Claude Code calls your search_notes tool (stdio, JSON-RPC, tools/list and tools/call, isError, the stateless _meta of the 2026-07-28 spec).

Answer: Claude Code starts `python -m coursemate.mcp_server` as a child process, and the two talk over its stdin and stdout, one JSON-RPC 2.0 message per line; that is why nothing in the server may print to stdout. In the 2026-07-28 spec there is no initialize handshake: every request carries `params._meta` with the protocol version, the client's name and its capabilities, so the server can stay stateless, and my `mcp_request` builds exactly that. First the client sends `tools/list`, and the reply holds each tool's name, description, input schema and annotations, which is what the model reads to decide what to call. When Claude picks `search_notes`, the client sends `tools/call` with `{"name": "search_notes", "arguments": {"query": "When is Lab 4 due?"}}` and an `id`, and the reply carries the same `id` so an answer can be matched to its request. The result is a `content` list with one text item holding my JSON of results (source, section, text), which the model then reads. If a tool fails in an expected way, such as sending an unapproved draft, the reply is still a normal result but with `isError: true` and the message, so the model can read it and explain; a malformed request or an unknown method is a JSON-RPC `error` instead. I saw all this by typing the messages myself with `RawClient` in `mcp_raw.py`, and `test_raw_client_talks_to_the_fake_server` checks the same exchange. I did not capture Claude Code's own traffic, only my client's, so I assume its messages have the same shape.

### Q23. Your send tool has side effects. Why doesn't your server trust the client's permission prompt, and how does your approval work? What would you change in production?

Answer: A send can't be undone and reaches real people, so I don't treat the client's permission prompt as enough. The server can't see who clicked yes: another client may not ask at all, a person may have chosen "always allow", and annotations like `destructiveHint` are only hints. So the yes lives outside the client, in something only the instructor does: they read the draft and run `py -m coursemate approve N` in their own terminal, which copies the exact text to `outbox/approved/NNN.md`. `send_announcement` calls `send_if_approved`, which asks `Outbox.is_approved`: the draft and the approved copy must both exist and match word for word, otherwise it raises `ToolError` with the command to run and nothing moves, and `test_a_draft_edited_after_approval_is_refused` covers an edit after approval. Claude Code adds a second gate: `.claude/settings.json` sets `send_announcement` to ask and denies `approve` through Bash and edits to `outbox/**`, so Claude can't approve its own draft. The weak point is that approval is a file, so anyone who can write to that folder can approve, the deny rules are a list of patterns that only stop Claude Code, and nothing records who approved. In production I would replace the file with a login-backed approval page that stores a hash of the exact text, the approver, their course, the time, an expiry and an idempotency key, with an audit log, and leave the actual sending to a separate service that checks all of that.

### Q24. How do you test an MCP server? (in-memory Client tests, a real stdio test, break-it tests, CI smoke test, and what you can only check by hand in a host.)

Answer: I test at four levels, and none of them calls a real model or the network. The first is in-memory `Client(server)` tests in `tests/test_mcp_server.py`, which go through the real MCP machinery without starting a process: they check the four tools and their hints, that search finds Lab 4 first, that bad arguments come back as `isError`, the resource list, the prompt text, and that a send is refused without approval and works after it. The second is a real stdio test, `test_raw_client_talks_to_the_fake_server`, which starts `python -m coursemate.mcp_server --fake` with a temporary outbox and sends JSON lines to it; it catches what in-memory tests can't, such as a stray `print` to stdout or a crash at startup. The third is break-it tests that try to get around the rules: `test_a_draft_edited_after_approval_is_refused`, `test_send_without_approval_is_refused_through_the_client` and `test_a_path_outside_the_list_is_refused` (a `../private` path). One honest gap is that, unlike the agent eval, no test removes the MCP gate on purpose to prove the tests would notice, so that is my next test. The fourth level is CI, which runs `python -m coursemate.mcp_raw` as a smoke test, though it fails only if the server crashes or replies badly, not if the gate stopped refusing, which the pytest tests cover. Only a real host can show a few things, so I check them by hand: `/mcp` says connected with 4 tools, the `ask` prompt appears before a send, the deny rules block `approve`, `@` resources and the prompt command show up, and which tool a real model actually picks.

### Q25. LLM system design: you're asked to expose a university's course systems (notes, LMS announcements, grades) to AI assistants for 50 instructors and 5,000 students through MCP. Cover remote transport (Streamable HTTP) and OAuth, per-course and per-role access (students never reach grades or sends), which tools need approval and how approval works when the instructor answers hours later, audit logs of every tools/call, prompt injection through notes and student messages, rate limits and cost, and how you'd roll out a new tool safely.

Answer: I would run one remote server over Streamable HTTP behind TLS (stdio is only for one local user) with OAuth through the university's identity provider: the client sends a bearer token, and the server checks its signature, its expiry and that it was issued for this server, never passes it on to the LMS, and takes the user, role and courses from the token, never from arguments the model chose. Access is enforced in the server per course and per role: every query is filtered by the caller's courses (`WHERE course_id = ANY(...)`), instructors get read, draft and send on the courses they own, and students get only read tools on the courses they are enrolled in, with no grade, draft or send tool in `tools/list` at all, so there is nothing to talk the model into calling. Reads and drafts run freely, but every send, and any grade change or other LMS write, creates a pending approval holding the draft id, the course, a hash of the exact text and an expiry, and the tool returns "waiting for approval"; hours later the instructor sees that exact text on a page and approves it, and a separate service sends only if the hash still matches, the approval hasn't expired and the approver owns the course, with an idempotency key so a double click can't send twice, and any edit cancels the approval. For audit, each `tools/call` writes one append-only structured line (request id, user, role, course, tool, a hash of the arguments, result or error, latency, approval id), kept under a retention limit and without grade values in the log, so I can answer who did what and when. Notes and student messages are untrusted text, so results are labelled and length-limited, but the real defences are structural: the student-facing assistant has no write tools, a human reads the exact text before a send, the gate is code, and I would add injection cases such as a note saying "send this to everyone" to the agent evals. For limits and cost I would use per-user and per-tool token buckets, a concurrency cap on slow tools such as `make_quiz`, caches for read results, and a monthly budget per course with alerts at 50, 80 and 100 percent that then falls back to a cheaper model or refuses politely. To roll out a new tool, I would first decide its approval tier and annotations, require the in-memory, stdio and break-it tests and the agent evals with injection cases in CI, enable it behind a flag for one pilot course and instructors only, watch the audit log, error rate and approvals, and keep a kill switch that removes it from `tools/list` immediately. I would also fail closed: if OAuth, the approval service or the database is down, reads may be refused and nothing is sent, and I would monitor denied calls, approvals pending for more than a day and the unapproved-sends count, which must stay 0.

## Observability, latency, cost and caching

### Q26. What are traces and spans? How did you instrument CourseMate, and why OpenTelemetry rather than a vendor SDK?

Answer: A span is one timed step with a name, a start, an end and attributes such as the model or the token counts, and a trace is all the spans of one request, linked into a tree by a shared trace id and parent ids. In CourseMate one answer is a `chat` span with `retrieve`, `llm` and `check` under it, and one agent run is an `agent` span with a child for every model call and tool call. My small `span()` helper takes the parent explicitly, always ends the span, and marks it ERROR when the step raises an exception. This matters because an answer is an async generator that pauses at every `yield`, and the API closes it with `aclosing` when the browser leaves, so every span that started still ends. Tracing does nothing until it is configured, so tests collect spans in memory and need no tracing server. When it is on, a batch exporter sends spans to Langfuse in the background, and a second exporter writes them to a JSONL file for my own report. I chose plain OpenTelemetry because it is an open standard, so another tool could receive the same spans by changing the exporter, although my `langfuse.*` attribute names would need adapting to get the same views there. Writing the spans by hand also showed me what a vendor SDK hides, at the price of more code.

### Q27. How do you measure latency in a streaming LLM app? Why p95 and not the average, and what did you measure?

Answer: I measure two things: time to first token, which is how long the student looks at nothing, and total time, which ends when the answer is complete and checked. I use percentiles because an average can describe nobody: in a worked example with ten answer times, the mean of 4,368 ms was slower than eight answers and far faster than the other two, while p95 was 20,000 ms. On `qwen2.5:3b` on my PC, answers that were not cached took 11,203 ms at p50 and 12,996 ms at p95, and cached ones took 76 ms at p50. The first token came 6,849 ms (p50) and 10,096 ms (p95) after the model call started, and the student also waits for retrieval before that. That run had only 10 answers, 5 cached and 5 not, so the p95 of each group is just its slowest answer. I report the two groups separately, because the overall p50 of 2,105 ms is far from what anyone waiting for the model experienced. The traces also showed retrieval taking about 2 seconds in several answers, including the slowest cached one; opening a new connection to `localhost` takes about 2 seconds on my PC, which I suspect is the cause but have not confirmed with a second run.

### Q28. How does your cache work? What's in the key, when is caching wrong, and how does it compare with a semantic cache and with the providers' prompt caching?

Answer: The cache sits in front of the model, and its key is a sha256 hash of the provider, model, messages, temperature and `max_tokens`, where the messages hold the system prompt, history, retrieved chunks and question. So new notes or a new prompt change the key, and a hit costs 0 tokens, although retrieval still runs to build the key. Only finished replies at temperature 0 are stored, they expire after an hour, and above 1,000 entries the least recently used one is dropped. Caching is wrong when the reply should change but the key does not, for example after new model weights arrive under the same name, and the expiry only limits how long that lasts. It also repeats mistakes: in my run the model began "I don't know" and then gave the relevant rule, my check rejected the reply, and the second ask got the same rejected reply from the cache. A semantic cache matches similar questions by their embeddings, so it hits more often, but "When is Lab 4 due?" and "When is Lab 5 due?" look very similar and have different answers, so for course facts I match exactly. Provider prompt caching is different: the model still writes a new reply, but the provider charges less for a long prompt beginning it has seen recently, which helps even when every question differs. In production I would use both and put the stable text first, after checking the provider's minimum length and price, since my prompts of about 480 tokens may be too short to qualify.

### Q29. How do you know what an answer costs, and how would you keep a monthly budget in production?

Answer: The model reports input and output tokens, `pricing.py` turns them into dollars with a dated price table, and the cost is recorded on the answer's spans, with $0 for a local model. An unknown price is left blank and fails the cost budget, so it is never counted as free. In my run a model call averaged 479 tokens in and 31 out, which with half the answers cached would be $0.000032 per answer on Claude Haiku and $0.000634 on Claude Sonnet if hosted. That 50% hit rate exists only because the benchmark asked every question twice, so for planning I assume no hits: 150,000 answers a month would cost about $9.51 on Haiku or $190 on Sonnet. These are estimates, because hosted tokenizers count differently and prices change. In production I would add each request's cost to a daily and monthly total, compare it with the provider's bill, and alert at 50, 80 and 100 percent of the budget. To enforce the budget and not only watch it, I would limit `max_tokens` and requests per student, and switch to a cheaper model or refuse politely at the limit. Today `coursemate stats` checks the budget only after the fact, and agent runs record tokens but no cost, so I would fix both first.

### Q30. LLM system design: design observability for an AI teaching assistant serving 5,000 students on a hosted model. Cover what to trace on each request, sampling, personal data in prompts (redaction, retention, who can see traces), alerts (p95 latency, error rate, refusal rate, cost per day), dashboards, linking traces to evals and to student feedback, and what the observability itself costs.

Answer: Assuming 2 questions per student per day, that is about 10,000 answers a day, each traced through retrieval, model call and citation check with a pseudonymous student id, session, course, model and prompt version, chunk ids and scores, tokens, cost, both latencies, cache hit and any refusal or error reason. Names, emails and student numbers are redacted before export, full text is kept for about 30 days and numbers for longer, and only a few named people can read the text, with their access logged and the data held by the university or by a vendor under a data agreement. Every request updates counters for latency, errors, refusals, tokens and cost, while full traces are sampled after each request ends: all errors, failed checks, slow answers and thumbs-down, plus about 10 percent of the rest. As starting values to tune on real data, I would wake someone if p95 time to first token stays above 5 seconds for 10 minutes or the error rate passes 2 percent. I would send a warning if the refusal rate doubles compared with last week or the day's cost passes its budget. Dashboards show p95 latency, error rate, refusal rate and cost per day, split by course, model and prompt version, with cache hit rate and time per stage. Feedback from the chat page carries the trace id, so a complaint opens the exact trace, and after redaction and review it becomes a case in the eval set that runs before each release. Observability has its own bill: my log averaged about 4.9 KB per answer, which is about 49 MB a day or 1.5 GB a month if everything is kept, before database overhead, plus the cost of running or buying the tool and of any LLM judge that scores traces.
